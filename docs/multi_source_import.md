# 本地存储与其他来源导入规划

状态：2026-09-13 的扩展设计，尚未实现通用文件导入或 SQLite 迁移。

## 当前已经具备

- `data/catalog/`：VitalDB目录快照与病例元数据。
- `data/tracks/<tid>/`：原始CSV、规范Parquet与包含来源/哈希/采样间隔的清单。
- `data/cases/<caseid>/`：病例通道清单、人工标记及追加历史。
- `data/runs/<run_id>/`：已完成分析、输入指纹、参数与结果。

这是持久的本地文件存储，不是SQLite数据库。读取本地数据仍需要磁盘读取、校验、JSON传输与浏览器绘图，不等于重新向VitalDB下载。相同数据/标记/参数/代码/元数据的运行现在在正式计算前命中结果缓存；读取时仍校验原始CSV与Parquet哈希。浏览器保存上次完成运行的ID和显示偏好，刷新后通过本地GET接口恢复，不创建新分析。完整点/概览的最近视图在当前页面内复用。

## 建议的多来源结构

继续用Parquet保存时序；增加SQLite管理来源、记录、通道映射、导入批次、标记版本与运行索引，避免将所有测量点放进单个JSON或关系表。SQLite适合当前单用户本地索引需求，不需要另建远程服务。

建议将记录身份扩展为`source_id + recording_id`，不能把其他来源记录塞入VitalDB整数caseid。现有VitalDB适配器、旧run_id和冻结清单保持可读取。各来源先转换为统一的`map / left / right / 可选辅助轨道`，再进入现有唯一计算内核。

## 接入一种新来源时必须明确

| 信息 | 需要确定的内容 |
|---|---|
| 文件与记录边界 | CSV/TSV/设备导出格式，哪个文件属于同一次记录 |
| 时间 | 相对秒数还是日期时间、时区、统一起点、设备时钟偏差；不按行号对齐 |
| 通道与单位 | 哪列是有创MAP，哪些列是左右rSO₂；mmHg/%等单位及必要转换 |
| 采样 | 原始时间戳、名义间隔、实际间隔统计；不得默认套用VitalDB的2秒/5秒 |
| 设备质量 | 缺失标记、明确的错误码、传感器无效标志；未定义错误码不猜测 |
| 来源与版本 | 来源名称、原始文件哈希、导入时间、转换规则版本、记录人群 |

导入流程应是本地选择文件 → 预览列/时间/单位/间隔与问题 → 确认映射 → 原文件只读归档及规范化 → 建立记录与通道索引 → 进入同一质量和COx流程。重复文件按哈希提示，失败导入不能成为“已完成”记录。

正式实现前需要一份实际来源文件或其字段说明，才能定义与验证适配器。日期/时钟仅在来源提供可信锚点时显示，不能从VitalDB相对时间推断。插值、逐搏MAP提取与信号延迟校正不作为导入时的隐式处理。

## 尚需改造的位置

`backend/car_core.analyze`已经接收规范通道与名义间隔，可继续共用；`services/vitaldb.py`、病例API的整数身份、导出来源文字以及前端病例选择目前仍与VitalDB绑定。未来应增加来源适配层及通用记录身份，配套不同单位、不同采样率、不同时间基准的夹具测试，再开放导入入口。
